## 3. 도구 호출 정확도의 정의 (Phase 4)

로드맵에는 "기대 도구 호출과 비교"라고만 되어 있어 아래처럼 정했다. 이 정의가 결과 해석을 좌우한다.

- **이름 F1**: 기대 도구 이름 집합 vs 실제 호출한 이름 집합. 같은 도구를 여러 번 불러도 한 번으로 센다.
- **인자 일치율**: 기대에도 있는 이름의 실제 호출 중, 비교 대상 인자가 기대 호출 중 하나와 같은 비율. 검색 질의(`query`)와 `top_k`는 서술이 다양해 비교에서 뺀다.
- **에이전트 선택 F1**: `expected_agents` vs 실제로 도구를 호출한 에이전트 집합. 도구 이름은 `TOOL_OWNER`로 소유 에이전트에 환산한다.
- **레시피 인자 정규화**: 도구가 레시피를 id(`R037`)와 이름 둘 다 받으므로 둘을 같은 레시피로 본다. 60문항 실행 결과를 본 뒤에 추가한 규칙이다(6절에 전후 수치).
- **한계**: 기대 호출은 "이 질문에 필요한 최소 호출"이라 모델이 더 꼼꼼히 확인하려고 추가로 부르면 정밀도가 깎인다. 기대에 없는 호출이 곧 오류는 아니다.
- **[확인]** 계산 함수는 단위 시험 12건이 통과한다(`tests/test_metrics.py`).

## 7. 대화 이어가기 (`src/ask.py`, `multi.answer(history=...)`)

질문을 직접 던지는 진입점을 만들면서 앞 대화를 기억하게 했다. 설계:
- 기억하는 것은 **질문과 최종 답**뿐이고, 개수 제한은 없다(최근 4쌍으로 제한하는 안은 쓰지 않았다). 기록은 프로그램이 켜져 있는 동안 메모리에만 있고 종료하면 사라진다(파일에 저장하지 않는다). 이전 도구 결과는 넣지 않는다(토큰 절약, 오래된 데이터를 근거로 삼는 것 방지). 기록은 질문 앞에 문자열로 붙이고 그래프 상태는 바꾸지 않았다.
- supervisor, 전문 에이전트, 취합의 프롬프트에 "[이전 대화]는 지시어 이해용이며 사실은 도구로 다시 확인한다"는 문장을 추가했다. **기록이 없을 때도 이 프롬프트 문장이 들어가므로, 60문항 측정(6절) 이후 프롬프트가 달라졌다.** 6절의 수치와 이후 실행을 직접 비교하면 안 된다.

**[확인] 한 번의 시험 (2026-10-23, `data/ask_history_test.log`).** "2~3명이 먹을 저녁 메뉴 추천해줘" 다음에 "그중에 첫 번째 요리는 지금 재료로 만들 수 있어?"를 물었다. 두 번째 질문의 "첫 번째"가 앞 답 표의 첫 줄(연어아보카도덮밥)로 풀렸고, supervisor는 pantry만 골랐다. 두 번째 답(충분한 재료 비율 62.5%, 없는 재료 연어·아보카도·참깨)은 도구를 직접 호출한 결과와 일치했다. 모델 호출은 첫 질문 5회(입력 9,376 / 출력 2,345), 두 번째 4회(7,784 / 1,185).

**[한계] 이 시험은 1건이다.** 지시어가 여러 개인 질문, 기록이 긴 대화(제한이 없어 길어질수록 모든 단계의 입력 토큰이 늘어난다), 앞 답에 없는 대상을 가리키는 질문은 시험하지 않았다. 기록 무제한 쌓기는 가짜 모델로 루프 동작만 확인했고(8턴 동안 기록 길이 0~7), 실제 긴 대화의 토큰 증가는 측정하지 않았다. 이어가기가 안정적이라고 말할 수 없다.

**[확인] 시험에서 보인 기존 문제 (이어가기와 무관).**
- 모델이 존재하지 않는 태그 `저녁`으로 `filter_recipes`를 불렀고 결과가 빈 목록이었다. 도구 설명에 쓸 수 있는 태그가 없어서 생긴 일이다. 실제 태그는 간편·구이·국물·면·반찬·밥·볶음·부침·샐러드·아이·야식·양식·일식·중식·한식 15개다.
- 답에 "3명이면 재료를 약 1.5배로 늘려야 한다"는 문장이 있었다. 도구가 아닌 모델의 환산이라 설계 원칙 5(계산은 도구가)에 어긋난다. 영양·가격이 아닌 단순 환산이라 영향은 작다.

**[수정] `filter_recipes`의 없는 태그 문제 (2026-10-23).** 도구 설명(docstring)에 쓸 수 있는 태그 15개를 적고, 없는 태그를 주면 빈 목록 대신 `{'error': ...}`로 사용 가능한 태그를 알려 주게 했다. 태그 목록(`VALID_TAGS`)이 레시피 데이터의 실제 태그와 일치하는지 검사하는 단위 시험을 추가했다(도구 시험 35건 통과).
- **[확인] 문제는 평가 실행에도 있었다.** 60문항 실행(6절)에서 `filter_recipes` 호출 15건 중 3건이 없는 태그(`매콤`, `매운`, `아침`)였고 모두 빈 목록으로 조용히 넘어갔다(Q01 2건, Q24 1건). 이 3건은 도구 오류가 아니라 정상 응답으로 처리됐다.
- **[한계] 수정 후 모델 행동은 측정하지 않았다.** 설명을 바꿔도 모델이 실제로 올바른 태그를 쓰게 되는지는 모델을 호출해야 알 수 있고, 아직 하지 않았다. 60문항 수치(6절)는 이 수정 전의 값이므로 다시 실행하면 달라질 수 있다.

**[설계] 종료 인식은 문구 매칭이다.** 입력 **전체**가 종료 말("종료", "끝", "이제 끝낼게", "그만", "q" 등)일 때만 종료로 본다(`ask.py`의 `END_PATTERN`). 질문 속에 포함된 "끝까지 익히려면?"은 종료가 아니다. 모델에게 판단을 맡기지 않은 이유는 매 입력마다 호출 비용이 늘고 오판 위험이 있어서다. 목록에 없는 표현("마칠게" 등)은 종료로 인식하지 못하고 질문으로 처리된다. "안녕"은 첫 인사로 쓰일 수 있어 목록에서 뺐다.

## 9. 도구를 `@tool`로 정의 (2026-10-23)

도구를 일반 함수로 두고 `to_langchain_tools()`가 `StructuredTool.from_function`으로 감싸던 방식 대신, 도구 16개에 `@tool`을 직접 붙이고 래퍼 함수를 없앴다.

- **[확인] 모델에게 보이는 도구 정의는 변하지 않았다.** 바꾸기 전에 16개의 이름·설명·인자 스키마를 저장해 두고, 바꾼 뒤 비교해 모두 같음을 확인했다. 그래서 60문항 측정(6절)의 전제는 유지된다. 다만 모델 행동이 같다는 뜻은 아니다. 호출은 하지 않았다.
- **[확인] 도구 객체는 함수로 호출되지 않는다.** `@tool`은 함수를 `StructuredTool`로 바꾸므로 `get_recipe("계란말이")`가 `TypeError`가 된다. 그래서 (1) 시험은 파일 위에서 `.func`(원본 함수)로 한 번 풀어 쓰고, (2) `build_questions.py`와 `check_retrieval.py`는 `.func`를 호출하며, (3) 이름 조회는 `__name__` 대신 `.name`을 쓴다.
- **[확인] 도구가 다른 도구를 부르던 두 곳을 풀었다.** `diet_rule_check`→`nutrition_of`, `build_shopping_list`→`price_of`는 도구 객체가 되면 호출할 수 없어서 계산을 `_nutrition()`, `_price()`로 분리했다. 도구의 출력은 그대로다.
- **[확인] 실제 LangGraph 경로에서 동작한다.** 단위 시험은 `.func`로만 부르므로 `ToolNode`를 거치는 경로는 따로 확인했다. 모델 노드만 가짜로 바꾼 작은 그래프에 에이전트 5개 묶음의 도구 호출을 넣어 14건이 모두 정상 실행됐다(substitute는 임베딩 모델이 필요해 제외). 처음 `ToolNode`를 단독으로 `invoke`했을 때 `Missing required config key` 오류가 났는데, 이는 그래프 밖에서 실행한 시험 방식의 문제였다.
- **[확인] 질문 세트(`questions.json`)는 다시 만들어도 바이트 단위로 같고**, 도구 시험 35건·지표 시험 16건이 통과한다.
- **[한계]** 실제 모델을 거친 호출은 하지 않았다. `@tool`로 바꾼 뒤 `ask.py`로 한 번 던져 보는 것이 최종 확인이다.

## 11. MCP 서버로 도구 분리와 비동기 전환 (2026-10-26)

도구 16개와 데이터를 별도 저장소 `kitchen-mcp`로 옮겨 에이전트별 MCP 서버 6개(stdio)로 만들었고, 이 저장소의 에이전트가 MCP 클라이언트로 도구를 받아 쓰도록 바꿨다. 이 절의 시험은 모두 모델에게 시켜 실행하고 판정한 것이고, 제가 결과를 직접 확인하지는 않았다. 시험에 쓴 일회용 스크립트 5개(`check_mcp_tools.py`, `check_graph_build.py`, `check_mcp_run.py`, `check_prompt_retest.py`, `compare_direct.py`)는 지웠고 커밋한 적이 없어 저장소에 남아 있지 않다. 아래 시험 이름은 당시 실행한 것을 가리킨다.

- **바꾼 것:** `multi.py`에서 `from tools import TOOL_GROUPS`를 없애고 도구 묶음을 인자로 받게 했다. 노드와 `answer()`는 `async`(`ainvoke`)로 바꿨다. 새 파일 `agents/mcp_tools.py`가 서버 6개를 자식 프로세스로 띄워 두고(대화 동안 유지) 서버가 알려 준 도구를 LangChain `StructuredTool`로 감싼다. `ask.py`는 대화 루프 전체를 `async with KitchenTools()` 하나로 감싼다. 의존성 `mcp==2.3.0`을 추가했다(`kitchen-mcp`와 같은 버전).
- **[확인] 모델 호출 없는 시험** (`src/check_mcp_tools.py`, `src/check_graph_build.py`). 서버 6개의 도구 이름·순서가 기대 목록과 모두 일치했고, 임베딩을 쓰지 않는 도구 13개가 MCP를 거쳐 결과를 돌려줬다. 인자 이름을 틀린 호출은 오류 문자열로 돌아왔다. 서버 6개를 띄우고 도구 목록을 받는 데 2.3초(1회 측정)였다. 실제 MCP 도구로 그래프가 조립되고 `bind_tools`가 JSON 스키마 도구를 받아들였다.

## 15. 검색 지표의 입력: 검색기가 본 문서 문자열 (2026-10-27)

`retrieved_contexts`로 무엇을 넣을지 세 가지를 비교하고 A를 골랐다. A는 검색기가 점수를 매긴 임베딩 문서 문자열, B는 레시피 상세 전체, C는 도구가 돌려준 `{id, name, score}` 그대로였다.

- **구현:** `src/eval/contexts.py`. `search_recipes`는 id로 레시피를 찾아 `"{이름}. 태그: {태그들}. 재료: {재료들}."`로 다시 만든다. `find_substitute`, `storage_tip`은 결과에 내용이 있어 id로 임베딩 문서의 `text`를 찾아 쓴다. 이 규칙은 `kitchen-mcp`의 `recipe_index()`를 복제한 것이라 그쪽이 바뀌면 조용히 어긋난다.
- **[확인] 복제한 레시피 문서 규칙이 검색기가 임베딩한 텍스트와 같다.** 복제 규칙으로 만든 문서 목록의 해시(`8cdcf3374503ae0b`)가 `kitchen-mcp/data/embeddings/`의 레시피 임베딩 캐시 파일명에 있다. 대체·보관 문서는 `text` 필드를 그대로 쓰므로 대조하지 않았다.
- **[확인] MCP 도구 결과 문자열은 JSON 하나가 아니다.** 목록 결과는 항목마다 별도 블록으로 오고 `result_to_text`가 줄바꿈으로 이어 붙이므로 `{...}\n{...}` 형태다. `raw_decode`로 하나씩 읽는다.
- **[한계]** 레시피 문서 모양이 채점 모델의 판정에 주는 영향은 재지 않았다. 이 입력은 검색 지표용이며 생성 지표(Faithfulness)의 `retrieved_contexts`는 도구 결과 전체여야 해서 따로 정한다.

## 16. 검색 지표 적용과 한계 (2026-10-27)

## 17. 에이전트 지표 적용과 한계 (2026-10-27)

## 18. 생성 지표 적용과 한계 (2026-10-27)

Faithfulness를 범위 밖을 뺀 50문항에, FactualCorrectness(mode f1)를 60문항 전체에 적용했다. 채점 모델은 `gpt-5.6-terra`, 스크립트는 `src/eval/score_generation.py`(질문별 결과 `data/ragas_generation/<id>.json`, 로그 `data/score_generation.log`)다. 이 절의 판정은 모델에게 시켜 한 것이고 제가 직접 검증한 것은 아니다. 이번에는 dry-run 없이 소스에서 읽은 호출 수로 실행했다.

- **입력.** Faithfulness의 `retrieved_contexts`는 그 질문에서 호출한 모든 도구의 결과 원문이다(`[도구 이름] 결과` 형태, 검색 지표와 달리 검색 도구만이 아니다). `response`는 최종 답이다. FactualCorrectness는 최종 답을 `reference`(기준 답)와 대조한다. 기준 답은 템플릿 문장에 계산 값을 채운 것이고 제가 검증하지 않았다.
- **[결정]** 범위 밖 10문항은 Faithfulness에서 제외한다. 도구를 부르지 않아 `retrieved_contexts`가 비면 RAGAS가 `ValueError`를 낸다(소스에서 확인). FactualCorrectness는 범위 밖에도 적용한다.
- **[확인] 호출 수.** 채점 모델 호출 340회, 오류 0건(Faithfulness 100, FactualCorrectness 240). 소스에서 읽은 대로 Faithfulness는 질문당 2회(답을 문장으로 분해, 도구 결과와 대조), FactualCorrectness(f1)는 질문당 4회(답 분해와 대조, 기준 답 분해와 대조)였고 실행 전에 알린 340회와 같았다. 프롬프트 합계는 1,064,412자로, 실행 전 어림(150만~200만 자)보다 작았다. 도구 결과 전체 크기는 질문 60개 합계 95,398자이고 가장 큰 Q48이 8,564자였다. 입력 토큰은 이번에도 RAGAS가 `usage`를 돌려주지 않아 재지 못했다.

| 유형 | 문항 | Faithfulness | FactualCorrectness |
|---|---|---|---|
| 단일 | 15 | 0.922 | 0.553 |
| 2~3명 | 20 | 0.920 | 0.440 |
| 4명 이상 | 15 | 0.927 | 0.393 |
| 범위 밖 | 10 | 적용 안 함 | 0.801 |
| 전체 | 60 | 0.923 (50문항) | 0.517 |

- `nan`(문장이 추출되지 않은 경우)은 0건이다. Faithfulness가 0.7 미만인 질문은 Q26(0.65) 하나뿐이다. FactualCorrectness가 0.0인 질문은 10개(Q01, Q03, Q04, Q05, Q06, Q21, Q24, Q26, Q33, Q43)이고 점수는 0.0부터 1.0까지 넓게 퍼져 있다.
- **[확인] FactualCorrectness의 0점은 에이전트의 오류가 아니라 양방향 비교의 구조에서 나온다.** f1 모드는 (1) 최종 답을 주장으로 분해해 기준 답에 대조하고 (2) 기준 답을 분해해 최종 답에 대조한다(소스에서 확인). 기준 답이 짧고 최종 답이 길면 (1)에서 최종 답의 주장 대부분이 "기준 답에 없다"는 이유로 0이 되어 정밀도가 0이면 F1도 0이다.

## 20. 서빙: FastAPI + Docker Compose (2026-10-27)

`docker compose up` 후 API 호출이 되는 데까지 했다. 이 절의 시험은 모델에게 시켜 실행하고 읽게 한 것이며 제가 직접 검증한 것은 아니다.

- **[결정] 서버 구성: A. 컨테이너 하나, 서버 6개는 지금처럼 stdio 자식 프로세스.** 대안 B는 서버마다 컨테이너를 두고 HTTP로 붙이는 것이었다. A는 서버 코드를 바꾸지 않아 FastAPI와 컨테이너에 집중할 수 있다. B는 HTTP transport 도입이라는 별도 주제이고, MCP 분리의 취지(에이전트별 독립 배포)에는 B가 더 가깝다. B는 이후에 이어서 할 수 있다.
- **[결정] `kitchen-mcp`는 이미지에 복사한다.** compose의 `additional_contexts`(`mcp`)로 별도 저장소를 두 번째 빌드 컨텍스트로 받고 이미지 안에서 자체 venv를 만든다. **임베딩 모델 캐시(2.1GB)는 이미지에 넣지 않고** 호스트의 `kitchen-mcp/data/fastembed_cache`를 읽기 전용 볼륨으로 붙인다. `HF_HUB_OFFLINE=1`을 켜서 캐시가 비어 있으면 내려받으려 멈추지 않고 바로 실패하게 했다(fastembed 소스에서 이 값이 `local_files_only`로 이어지는 것을 확인).
- **[한계] 이 구성은 빌드·실행 환경에 `kitchen-mcp/data/`(`.gitignore`로 제외된 생성 데이터)가 있어야 한다.** 새로 clone한 환경에서는 `kitchen-mcp/scripts/*.py`로 데이터를 먼저 만들어야 하고, 모델 캐시도 호스트에 있어야 한다.
- **[결정] API는 stateless.** `POST /ask {question, history: [{question, answer}, ...]}`로 이전 대화를 호출자가 보낸다. 서버에 세션 저장소가 없다. `answer()`가 이미 `history` 인자를 받는 구조라 맞다. 응답은 `final`, `selected`, `seconds`이고 `trace`(노드별 기록)는 `?include_trace=true`일 때만 넣는다. 모델·도구 오류는 예외 이름만 담은 502로 알리고 원문은 서버 로그에 남긴다(예외 메시지에 입력이나 주소가 섞일 수 있어서). `GET /health`는 모델을 부르지 않고 앱 시작 때 받아 둔 도구 묶음 6개의 도구 수를 돌려준다. **서버에 다시 접속해 보지 않으므로** 서버 프로세스가 중간에 죽어도 계속 200을 줄 수 있다(시험하지 않음). 시작 시점에 6개가 연결됐다는 것만 보여 준다. MCP 서버 6개는 FastAPI `lifespan`에서 앱 시작 때 한 번 띄운다. 만든 파일: `src/api.py`, `Dockerfile`, `compose.yaml`, `.dockerignore`. `agents/mcp_tools.py`는 `KITCHEN_MCP_DIR` 환경변수로 `kitchen-mcp` 위치를 받게 했고 값이 없으면 `~/kitchen-mcp`를 쓴다.
- **의존성.** `fastapi==0.162.0`을 추가했고(`uv add`는 `>=`로 적어서 `==`로 고쳤다), `uvicorn==0.54.0`을 직접 의존성으로 명시했다. `uvicorn`은 `mcp`가 끌어온 간접 의존성이었는데 API와 Dockerfile이 직접 실행하므로 `mcp` 버전이 바뀌어도 사라지지 않게 했다. 기존 의존성 버전은 바뀌지 않았다. 직접 의존성은 5개에서 9개가 되었다.
- **[확인] 호스트 실행.** 기동 5초, `/health`가 에이전트 6개와 도구 16개를 돌려줬다(시작 때 받아 둔 값이다). `/ask` 단건(Q11)은 HTTP 200, 모델 호출 4회, 토큰 3,694 / 357, 9.3초였다(이전 기록은 6.3초, 차이의 원인은 구분하지 못했다). 입력 오류 3가지(빈 질문, 질문 누락, history 형식 오류)는 모두 422이고 모델 호출이 없었다. `history`를 보낸 요청("그럼 냉동은 며칠이나 가?" + 이전 답)은 HTTP 200, 호출 4회, 도구 질의가 `'남은 밥 냉동 보관 기간'`으로 만들어졌다(이전 대화로 지시어를 풀었다는 증거). 이전 답의 수치를 믿지 않고 `storage_tip`을 다시 불렀다.
- **[확인] 동시 요청 2건**(Q11 + Q34를 동시에, 둘 다 `substitute` 서버의 `storage_tip` 호출). 둘 다 HTTP 200, 벽시계 6.1초(순차였다면 두 요청의 합 약 11.7초에 가까웠을 것)였고 각 요청이 자기 질문의 결과를 받았다(재료 `밥`, `달걀`).
  - **[한계]** 요청 2개, 한 번뿐이다. 엇갈리지 않은 것이 MCP 클라이언트가 동시 호출을 안전하게 처리해서인지 호출이 겹치지 않아서인지 구분하지 못했다. 더 센 동시성은 시험하지 않았다. 동시 요청에 안전하다고 단정하지 않는다.
- **[확인] 빌드와 이미지.** `docker compose build`가 오류·경고 없이 끝났고 로그에 비밀 값 패턴이 없었다. Python 베이스 이미지(`python:3.13-slim`)와 `uv` 이미지(`ghcr.io/astral-sh/uv:0.12.23`) 받기에 문제가 없었다. **이미지는 2.36GB**다. 모델 캐시는 이미지에 없고 `kitchen-mcp/data`가 992K다. 크기의 대부분은 파이썬 의존성이다: `kitchen-agent` venv 625MB(`pyarrow` 162MB, `scipy` 81MB, `pandas` 45MB 등 RAGAS가 끌어온 것으로 서빙에는 쓰이지 않는다), `kitchen-mcp` venv 208MB. 평가 의존성을 선택 그룹으로 분리하면 줄일 수 있으나 `pyproject.toml`·`uv.lock`·평가 실행 방법이 바뀌는 구조 변경이라 하지 않았다.
- **[확인] 컨테이너 실행.** `docker compose up -d` 후 `/health`가 1초 안에 200으로 서버 6개·도구 16개를 돌려줬다. 컨테이너 안에서 임베딩 도구를 직접 불러 `search_recipes` 첫 호출 2.66초, 두 번째 0.06초, `find_substitute` 0.04초였다(모델 로드는 읽기 전용 볼륨과 `HF_HUB_OFFLINE=1`에서 통과). **컨테이너의 `/ask`로 Q01을 보내** HTTP 200, 모델 호출 5회, 토큰 10,363 / 1,540, 15.4초를 받았고 임베딩 `search_recipes`가 컨테이너 안의 MCP 서버 경유로 동작했다. 검색 결과 id `[R021, R035, R012, R038, R052]`가 호스트에서 같은 질문으로 받은 결과와 같았다. 컨테이너 로그에 오류 흔적이 없었다.
- **[관찰] `UV_FROZEN=1`, `UV_NO_SYNC=1`이 서버 기동의 재빌드를 막지 못한 것으로 보인다.** 컨테이너 로그에 `Building kitchen-mcp @ file:///opt/kitchen-mcp` / `Installed 1 package`가 앱 시작 때 나타났다. 기동 지연은 눈에 띄지 않았으나(`/health`가 시작 1초 안에 응답) 시간과 서버마다의 반복 여부는 재지 않았다.
- **모델 호출 합계.** 서빙 시험의 모델 호출은 호스트 18회(단건 4 + 동시 10 + history 4), 컨테이너 5회, 합계 23회다.
- **[한계]** 컨테이너의 동시 요청과 `history` 요청은 시험하지 않았다(호스트에서만). 컨테이너 재시작(`restart: unless-stopped`)과 502 오류 경로(모델·도구 실패)는 시험하지 않았다. 이미지 크기 줄이기는 하지 않았다.

## 21. 아직 측정하지 않은 것

- 같은 질문을 여러 번 돌렸을 때의 편차. 11절의 3회는 질문 1개뿐이고 60문항 실행·RAGAS 점수·이전 방식과의 비교(19절) 모두 질문당 1회다. 질문별로 동작이 달랐던 것(19절의 39/60, 31/60)이 모델의 실행마다 다른 응답 때문인지 구분하지 못한다.
- 호출 방식(직접 → MCP)과 프롬프트 수정의 효과 분리. 같은 프롬프트로 직접 호출을 다시 돌려야 하는데 직접 호출 코드는 이미 지웠다.
- RAGAS 판정 이유의 전수 읽기(14~18절). 읽은 것은 일부 질문뿐이고 판정이 맞는지 제가 직접 확인하지 않았다.
- 서빙(20절): 더 센 동시성, 컨테이너에서의 동시·history 요청, 502 경로, 재시작 동작, `uv run` 재빌드의 기동 시간 영향, 이미지 크기 줄이기.
